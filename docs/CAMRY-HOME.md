# Camry Home — 0.1.35

Camry is an optional mode inside the existing APK. OEM forwarding remains the default. New Home, Dock and ZLink-startup preferences default to off and do not migrate or overwrite MODE assignments.

## Home-only routing and window restoration (0.1.28 / code 29)

Enable **ZLink only in Home window** in Current settings. This default-off switch also enables Camry Home and experimental window mode. CarMode Apps, MODE and Dock launches of the default ZLink package or the selected Android Auto package route to Home, preserving the requested Activity component. The Home host then measures its target and requests the bounded task. Failed window launches report an error without an ordinary fullscreen fallback while this switch is enabled. Disabling Home/window mode or performing rollback clears the switch.

Native Home entry reopens the window automatically. Returning focus from a bounded ZLink task now requests restoration too. Each return attempt is consumed before launch and is rearmed only after Home remains visible behind the bounded window for 750 ms; firmware repeatedly ignoring bounds cannot cause an endless fullscreen relaunch. Apps/settings navigation suppresses competing restoration. Back on CarMode itself cancels pending restoration and keeps the five-Back escape available. No global Back interception is used. External launchers, ZLink's own maximize controls and firmware decisions cannot be redirected by this app-level switch.

The signed APK passed 176 JVM tests and the existing bytecode/signature checks. API 29 emulator checks used a separate schematic ZLink fixture: native Home and bounded Back restored it without a tap; selecting its Apps tile and the Dock Music action returned to Home with the bounded task at `[0,24][1216,672]`. Music uses the same dispatcher as MODE; physical CAN/MODE delivery and real ZLink remain head-unit checks. Five Back presses on the focused CarMode root cleared the feature flags and returned to OEM Fixture. Evidence: `docs/local/camry-0.1.28-home-return.png`, `camry-0.1.28-back-return.png`, `camry-0.1.28-apps-window.png`, `camry-0.1.28-mode-route.png`, `camry-0.1.28-rollback.png`.

### OEM app windows: freeform investigation

The head-unit photos supplied on 2026-10-28 show Google Maps in the OEM launcher's central area, surrounded by its own controls. The available OEM decompilation contains a concrete candidate mechanism: `Workspace.startFreeformActivity` and CAR_HOME_V5's `Utils.startFreeformActivity` call `ActivityOptions.setLaunchBounds(rect)` and then `startActivity(intent, options)`. Launcher/Workspace also check `ro.auto.homefreeform` and send `action.hcn.launcher.freeform.start` / `.move`; Launcher receives `.stop`. This is evidence of OEM freeform integration, rather than proof that Maps is a child View in the launcher.

Unlike the newer [cross-application activity embedding](https://developer.android.com/develop/ui/views/layout/activity-embedding#cross-application_embedding) API, [setLaunchBounds](https://developer.android.com/reference/android/app/ActivityOptions#setLaunchBounds(android.graphics.Rect)) is public since API 24. Its bounds can be ignored when the device/display does not support the relevant window modes. Therefore Android 10 alone does not rule out bounded external-app windows for CarMode. The OEM manifest declares `android.uid.system`, but that declaration does not establish that this particular public call requires a system UID.

The exact Map/Video button path in the photographed theme, firmware window-management policy, and ZLink's response to bounded launch remain unverified. The launcher loads theme-provided `MainLayout` code, so the main APK and bundled CAR_HOME_V5 module are insufficient to trace every theme action. No claim is made yet that CarMode can reproduce the OEM composition, maintain its window layering, or show separate Maps and AIMP apps simultaneously.

Enable **ZLink in Home window (experimental)** in the Current tab, then open Camry Home: ZLink opens automatically once the screen is focused and its bounds are stable. Tap the target area to retry after a failure. The right rail is fixed at 64 dp, with four 52 dp icon buttons: camera, apps, CarMode settings and Android settings. Labels remain in tooltips/content descriptions. Dock controls, window-mode disable and OEM rollback remain in settings; five local Back presses still provide rollback. The target gets the remaining width and full usable height, intersected with the usable window frame; system navigation remains outside the rectangle. A bounded launch closes an existing Dock session. Changing language/settings rebuilds Home on return. Each explicit Android Home entry requests the window once, with no pinning or recurring retry; fullscreen Back returns use the bounded-restoration policy below. External windows are OS-managed: a launcher View cannot clip them or prevent a ZLink child Activity/firmware from changing bounds. Close and reopen an external window after changing the Home layout; bringing an old task forward can retain its old bounds.

`CamryNavigation` places HomeProxyActivity beneath ordinary ZLink launches in Camry mode, using `startActivities` and `NEW_TASK | TASK_ON_HOME`, including MODE/Dock launches of the default ZLink package. Bounded launches from an existing Home/preview start directly over that host: rebuilding Home between measurement and launch would invalidate its coordinates. This prevents an older OEM task from being the ordinary Back destination in the tested stack scenario. It does not intercept external Back or override an explicit OEM launch performed by ZLink. When Camry is off or recovery is active, the original direct-launch route is retained. The protected real ZLink APK does not expose its Back implementation in the available decompilation; head-unit confirmation remains necessary.

`CamryAppWindow` uses `NEW_TASK` and public `setLaunchBounds`, without the adjacent/split-placement hint `LAUNCH_ADJACENT`. A bounded launch waits for two equal visible screen rectangles 250 ms apart, for at most eight checks. Input/navigation cancels this wait; an unready layout reports an error instead of launching with transient bounds. In Android 10's [TaskLaunchParamsModifier](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android10-release/services/core/java/com/android/server/wm/TaskLaunchParamsModifier.java), bounds alone do not select freeform on a fullscreen display. The experiment therefore also sends the internal ActivityOptions bundle hint `android.activity.windowingMode=5` (freeform), as defined by AOSP Android 10 [ActivityOptions](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android10-release/core/java/android/app/ActivityOptions.java). This is a firmware-dependent internal protocol, not a supported public embedding contract. A rejected mode request falls back once to the bounds-only OEM call; a launch failure falls back to ordinary launch only when Home-only routing is off and this is not a restoration attempt, while an unready target area waits briefly and reports an error. Accepted requests may still be shown fullscreen by Android, and already-running tasks can retain prior bounds. Logs explicitly record `bounds_confirmed=false` and `foreground_confirmed=false`; acceptance is not proof of embedding.

No system properties/settings, root commands, reflection, privileged permission requests, external-task resizing, pinning or global navigation hooks are added. The setting defaults off, and the durable OEM rollback also clears it. In Camry window mode, Home entry owns automatic opening independently of the ordinary once-per-boot startup preference. That startup path is skipped to prevent competing launches. OEM-forwarding startup retains ordinary launches; Dock Music routes to Home when Home-only routing applies.

With freeform support temporarily enabled on the diagnostic emulator and Android restarted, the same CarMode APK launched the separate demo app in an OS-managed freeform task at `[16,136][952,600]`, exactly matching the Home target area. Both Camry Home and the external app were visible, with Android navigation and a system-provided window caption. Evidence is in ignored `docs/local/camry-window-freeform.png` and `camry-window-freeform-activities.txt`. This proves a windowed external demo task, not real ZLink compatibility or separate live Maps/AIMP embedding. Disabling window mode returned Home to the front; disabled-target launch stayed on Home without crashing; five Back presses cleared all four flags and returned to OEM Fixture. Native Home and Recents remained available. The emulator-only global freeform setting was restored to its previous absent value after the test; the APK never changes it.

Icons and labels form one centred group within each button, with shared padding and button semantics. Camry panels/buttons and the MODE menu frame/cards have square corners. Camry buttons retain touch feedback through rectangular ripple backgrounds. The floating Dock container is transparent, without a background card or outline; individual button backgrounds and the normal Android Auto Home card's accent outline are retained.

## Startup and recovery

Window mode automatically opens ZLink once per explicit Home entry, without requiring a tap and independently of the ordinary boot-startup switch or a previously consumed boot claim. Returning from Camry's camera/settings actions also requests the window; returning from Apps to Home starts a new entry. `HomeWindowEntry` consumes each request before scheduling stable-bounds checks, so repeated focus callbacks cannot retry indefinitely. Preparing Home underneath an ordinary fullscreen ZLink launch does not issue a competing window request. Apps navigation opens a dedicated fullscreen application task above the existing freeform task. Local Back on CarMode cancels pending automatic entry; returning focus after closing bounded ZLink requests restoration under the bounded return policy above. Rollback and feature disable still stop both entry and fullscreen-return requests.

Latest API 29 emulator verification: 169 JVM tests and six bytecode checks passed. Without clicking the ZLink area, the demo window appeared on plain Home, repeated system Home, return from settings, return from Apps and Android reboot with the ordinary boot-startup switch off. The boot claim remained unchanged while the window appeared at `[0,24][1216,672]`. This verifies foreground window-entry routing, not real head-unit ZLink rendering. Evidence: `docs/local/camry-auto-home-entry.png` and `camry-auto-home-after-boot.png`.

In window mode, returning to an existing Camry Home after ZLink covered it fullscreen requests one bounded relaunch once Home has focus and stable bounds. `ZlinkReturnPolicy` consumes the attempt before launch. It rearms only if Home remains visible beside the restored window; a firmware that ignores bounds cannot create repeated fullscreen Back/relaunch cycles. Closing an already bounded window does not reopen it. Explicit Home navigation, app-grid/settings navigation, local Back, feature disable and recovery discard a pending return. This return action is separate from the once-per-boot startup claim. Emulator checks covered two fullscreen/Back round trips, no relaunch after bounded Back, and five-Back rollback. The real ZLink Activity implementation still needs device verification.

Automatic ZLink startup is opt-in and only scheduled by a visible HOME Activity after rendering. A synchronous `camry_startup_epoch` claim is saved before the delayed attempt. `ZlinkStartupPolicy` rejects a consumed Android `BOOT_COUNT`, crash recovery, disabled startup or an ineligible screen. Activity/process recreation, failed launches, Home and Back cannot retry that boot claim. User interaction, pause and relevant setting changes cancel delayed work. An ALL_APPS request never schedules startup.

In Camry mode startup leaves Camry Home behind ZLink. In OEM mode a temporary Camry startup view hosts the attempt; unsuccessful/cancelled attempts return to OEM while the host is foreground, and a return after ZLink forwards to OEM. No boot receiver, service or broadcast launches ZLink in the background. The explicit Android Auto button always remains a manual launch action.

Unknown `BOOT_COUNT` uses a single persisted `unknown` claim, rather than assuming process recreation means a new boot. A later readable boot identity permits a new attempt. No physical ACC-cycle guarantee is made: sleep/wake may leave Android running. Launch requests and scheduling/skip reasons are recorded; they are not proof of foreground display or phone/audio readiness.

`CamryControl` is shared by Home, settings, Dock and recovery. Rollback first cancels pending startup and closes Dock, then commits Home, startup, Dock and experimental window mode as off in one edit and explicitly opens Launcher3. MODE enablement, HCN, app assignments, Music HTTP and original runtime startup are retained. A recovery page remains behind the launch request. Failed durable saving is reported rather than claiming success.

The separate stock-launcher action opens Android Home settings even if saving fails. The actual resolved Home is checked on return, including cancelled selection. Camry activation requires the exact OEM Activity and a system Home-settings handler to exist. Neither activation nor installation silently changes Android Home. The app-icon entry still routes directly to settings or crash recovery without initializing the new Home UI. Localization falls back to English if preferences cannot be read.

Five distinct Back presses in a fixed five-second window execute the same durable rollback without confirmation. The first four preserve ordinary Back navigation; the root Camry Home stays open so the sequence can finish. The gesture is local to CarMode and cannot observe Back inside ZLink. Use Restore OEM in the expanded Dock there. Recovery remains accessible when Launcher3 or system settings cannot be opened.

To remove CarMode completely: restore the previous behaviour, select Launcher3 in Android Home settings, verify system Home, then uninstall. Reboot/recreation does not re-enable new features after rollback.

### Repeated Android Home chooser after emulator tests

On 2026-10-28 this was reproduced on the diagnostic Android 10 emulator. With OEM Fixture saved as Home, installing an additional HOME-capable test app changed the candidate set. Android logged `Result set changed, dropping preferred activity` and downgraded the saved choice to a last-used entry. The next system Home showed exactly "Use OEM Home fixture as Home", with Just once / Always and CarMode under the other-app list. Just once reproduced the same chooser on the next Home press. Selecting a row under "Use a different app" also launches that alternative once; use Always when it becomes the selected Home, or select the app through Android Home settings.

This explains the state left by the earlier destructive rollback test: CarMode had been uninstalled and then installed again, adding a HOME candidate back to the emulator. Updating the same installed APK with `install -r` did not reproduce the reset. Repeated Home presses and switching between Camry and OEM-forwarding modes preserved a saved default. The platform's candidate-set invalidation is visible in the Android 10 [PackageManagerService preferred-activity logic](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android10-release/services/core/java/com/android/server/pm/PackageManagerService.java).

Diagnostic cleanup must remove temporary HOME candidates first, then explicitly restore the intended Android Home through the system selector, and finally verify `resolve-activity`, repeated native Home presses and the internal Home mode. Do not leave a shared review emulator immediately after uninstall/reinstall testing without checking its Home choice. For Camry, choose CarMode Bridge as the permanent Android Home and enable Camry mode; choosing OEM Fixture permanently intentionally opens the stock stand-in instead. The internal Home mode switch alone does not assign the Android HOME role.

After removing the temporary probe and choosing CarMode Bridge with Always, eight native Home presses opened Camry without a chooser. An Android reboot preserved both the HOME role/preferred component and enabled Camry mode; three further native Home presses also opened Camry directly. No application-code change was needed for this Android preference repair.

## Camera and navigation boundaries

There is no verified reverse-gear signal. The existing optional Accessibility diagnostics do not establish camera exclusion, and the public HCN MODE broadcast is not evidence of reverse gear. A Camera action through CarMode closes the previous Dock before resolving/launching, then requests a new automatic Camry session after launch succeeds. The default camera app selected from the app list also requests this session. Screen-off, display-configuration changes, lost overlay permission and rollback close the session.

An OEM reverse-camera surface may not send any usable signal. Automatic Dock is requested after launches made through CarMode, not by a reverse-gear detector. If the vehicle opens a camera without a CarMode transition or a covered Camry Home, no automatic Dock appearance is guaranteed. Overlay visibility over native camera surfaces depends on firmware.

No immersive/hide-navigation flags, lock-task/kiosk mode, global Back hook or Home/Recents capture are introduced. Camry's Apps button lists installed launchable apps, separately from system Recents. Actual system-bar visibility over ZLink/native camera surfaces and OEM Recents integration still depend on firmware and those windows; JVM tests do not establish them.
